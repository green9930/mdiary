# 구버전 분석: 다씀 (mdiary v1)

> 기준: `main` 브랜치 (마지막 커밋 2023-09-07, 커밋 72개).
> 리뉴얼은 구버전을 참고만 하고, 초기 세팅부터 모든 방식을 다시 결정한다. 이 문서는 그 논의의 출발점이다.

## 1. 서비스 개요

- **이름**: 다씀 ("내가 얼마 썼는지만 알고 싶을 때")
- **기획 의도**: 계좌·카드 연동, 결제 수단 관리 같은 부가 기능 없이 **지출 내역만** 기간·카테고리별로 보는 가계부
- **대상 환경**: 모바일 우선 (레이아웃 최대 폭 601px), PWA로 홈 화면에 설치해서 사용
- **운영 기간**: 2023-01 ~ 2023-09 (실제 개발 기간은 약 2개월, 9월에 일부 업데이트)

## 2. 기능 목록

### 2-1. 화면

| 경로           | 화면                | 기능                                                                                                                                                        |
| -------------- | ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/` (비로그인) | 로그인              | Google 로그인, 체험해보기(테스트 계정), GitHub 소개 링크                                                                                                    |
| `/`            | 월간 (Monthly)      | 직접 만든 달력에 날짜별 지출 합계 표시, 월 합계, 월·연 이동, 연·월 직접 선택, 날짜 선택 시 해당 일 내역 목록, "M/D 추가하기"로 그 날짜의 작성 화면으로 이동 |
| `/weekly`      | 주간 (Weekly)       | 일~토 한 주의 요일 탭, 주 합계, 주 단위 이동, 선택한 날의 내역 목록 (제목순 정렬)                                                                           |
| `/new`         | 작성 (New)          | 날짜, 제목, 카테고리, 내용, 금액 입력, 정산하기 계산기                                                                                                      |
| `/daily`       | 일간 (Daily)        | 하루 합계, 하루 단위 이동, 날짜 직접 선택, 내역 목록                                                                                                        |
| `/categories`  | 카테고리 (Category) | 카테고리(전체 포함) 및 월 선택, 해당 월 합계, 날짜 내림차순 목록                                                                                            |

- 상단 고정 내비게이션: MONTHLY / WEEKLY / NEW / DAILY / CATEGORY, 로그아웃 버튼
- 인증이 필요한 경로에 로그인하지 않고 들어가면 로그인 화면을 보여준다 (리다이렉트 없이 같은 경로에 렌더링).

### 2-2. 지출 내역 (CRUD)

- **필드**: 날짜, 제목, 카테고리, 내용(선택), 금액
- **검증**:
  - 필수: 날짜, 제목, 카테고리, 금액(0 불가)
  - 길이 제한: 제목 25자, 내용 200자, 금액 9자리
  - 금액은 숫자만 받고 천 단위 쉼표로 표시
- **조회**: 목록 항목(카테고리 아이콘, 제목, 금액, 날짜) → 상세 모달
- **수정**: 상세 모달 안에서 편집 화면으로 전환
- **삭제**: 확인 모달을 거쳐 삭제
- 작성·수정·검증 실패를 알리는 결과 모달

### 2-3. 카테고리 (9개, 고정)

가전, 교통, 문화생활, 미용, 식비, 의료, 의류, 학비, 기타

### 2-4. 정산하기 (2023-09 추가)

작성 화면에서 금액을 계산해 넣는 보조 기능이다.

- **차액**: 지불 금액 − 받은 금액 (받은 금액이 더 크면 확인 불가)
- **1/n**: 지불 금액 ÷ 인원 수

## 3. 기술 스택과 개발 방식

| 영역        | 구버전 방식                                                                                 |
| ----------- | ------------------------------------------------------------------------------------------- |
| 프레임워크  | Create React App 5, React 18, TypeScript 4.9                                                |
| 라우팅      | React Router 6 (`BrowserRouter`, `basename`에 GitHub Pages 경로)                            |
| 상태 관리   | Redux Toolkit (user, expend 두 개의 slice). recoil은 설치만 하고 사용하지 않음              |
| 스타일      | styled-components 5 + theme 객체, `calcRem` 유틸                                            |
| 아이콘·폰트 | react-icons, 웹폰트는 CDN에서 불러옴 (Tenada, KorailRoundGothicBold, Rubik)                 |
| 데이터 통신 | Firebase SDK로 클라이언트가 Firestore에 직접 접근. axios는 설치만 하고 `api.ts`는 비어 있음 |
| 테스트      | CRA 기본 설정만 있고 테스트 코드는 없음                                                     |

### 3-1. 유저 인증

- **Firebase Authentication**
  - Google 로그인 (`signInWithPopup`)
  - 체험해보기: 미리 만든 테스트 계정으로 이메일·비밀번호 로그인. 비밀번호는 `REACT_APP_` 환경변수로 넣어서 빌드 결과물에 그대로 포함됨
- 로그인 유지: 앱 시작 시 `onAuthStateChanged`로 확인하고, 그동안 로더를 보여준다.
- 로그인한 유저 정보(이메일, 표시 이름, uid)를 Redux에 저장한다.

### 3-2. 데이터 관리

- **저장소**: Cloud Firestore, `expend` 컬렉션 하나
- **문서 구조**: `{ category, title, content, date: "YYYY-MM-DD", price: "숫자 문자열", username }`
- **소유자 구분**: 유저 uid가 아니라 **Google 표시 이름(`displayName`)** 으로 구분한다.
- **조회**: 로그인할 때 `username == 표시 이름`인 문서를 **전부 한 번에** 가져와 Redux에 넣는다. 월·주·일·카테고리 필터와 합계 계산은 모두 클라이언트에서 한다.
- **쓰기**: 컴포넌트와 유틸 함수에서 `addDoc`, `updateDoc`, `deleteDoc`을 직접 호출한 뒤 Redux에도 반영한다.
- **보안 규칙**: 저장소에 Firestore 보안 규칙 파일이 없다. 어떤 규칙을 썼는지 코드로는 확인할 수 없다.

### 3-3. 배포와 운영

- **호스팅**: GitHub Pages (`gh-pages -d build`, `https://green9930.github.io/mdiary`)
- **PWA**: CRA의 Workbox 서비스워커와 manifest를 쓰고 아이콘을 크기별로 준비했다. 설치 유도 버튼 코드는 주석 처리돼 있다.
- **분석 도구**: GTM 스니펫(`index.html`), react-ga4 코드 (페이지뷰 추적은 주석 처리)
- **CI**: 없음. 로컬에서 빌드해 배포
- **환경변수**: Firebase 설정, 테스트 계정 비밀번호, GA·GTM ID. 모두 `REACT_APP_` 변수라 빌드 결과물에 포함된다.

## 4. 구조적 문제와 한계

리뉴얼에서 같은 문제를 반복하지 않으려고 정리한다.

| 구분        | 문제                                                                                                   | 영향                                                                             |
| ----------- | ------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------- |
| 데이터 소유 | 표시 이름으로 소유자를 구분                                                                            | 이름이 같은 유저끼리 데이터가 섞이고, 이름을 바꾸면 기존 데이터에 접근할 수 없음 |
| 데이터 조회 | 전체 내역을 한 번에 가져와 클라이언트에서 필터                                                         | 데이터가 쌓일수록 첫 로딩이 느려짐                                               |
| 데이터 타입 | 금액이 문자열, 날짜가 `YYYY-MM-DD` 문자열                                                              | 금액 정렬이 문자열 비교로 동작함 ("9000" > "10000")                              |
| 상태 동기화 | `addExpend` reducer 안에서 비동기로 Firestore를 다시 조회해 id를 채움 (reducer에 부수효과가 있음)      | 새 항목의 id가 비어 있을 수 있어, 등록 후 `window.location.reload()`로 우회      |
| 보안        | 테스트 계정 비밀번호가 빌드 결과물에 포함됨. 보안 규칙을 저장소에서 관리하지 않음                      | 체험 계정이 오용될 수 있음. 접근 제어를 검증할 수 없음                           |
| 코드 구조   | 날짜 계산이 컴포넌트마다 중복됨. 모달 상태가 내역 항목마다 흩어져 있음                                 | 유지보수가 어렵고 버그가 생기기 쉬움                                             |
| 품질        | 테스트와 CI가 없음. 쓰지 않는 패키지(recoil, axios, universal-cookie, react-device-detect)가 남아 있음 | 회귀를 막을 장치가 없음                                                          |
| 기능        | 연도 선택은 최근 5년만 가능. 반복 지출·할부·통계·검색 없음                                             | 장기간 사용하기 어려움                                                           |

## 5. 리뉴얼에서 다시 결정할 항목

구버전 방식은 참고만 하고, 아래 항목을 0부터 논의해서 정한다. 각 항목이 몇 단계에서 정해지는지 함께 적었다.

| 영역            | 결정할 것                                                                                                                                                                                                                                                                                                                                                    | 단계 |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---- |
| 서비스 정체성   | **"지출만 간단히" 기조를 유지하고 일부만 확장한다 (결정됨).** 정기지출·할부, 간단한 월간 통계 정도. 예산·수입·계좌 연동은 넣지 않는다                                                                                                                                                                                                                        | 1    |
| 대상 플랫폼     | **모바일 웹 + PWA 우선 (결정됨).** 데스크톱에서는 모바일 레이아웃을 가운데 정렬해 보여준다                                                                                                                                                                                                                                                                   | 1    |
| 체험하기        | **체험 방식을 두지 않는다 (결정됨).** 공용 테스트 계정·데모 모드 없이 Google 로그인만 제공                                                                                                                                                                                                                                                                   | 1    |
| 기능 범위 (MVP) | **결정됨:** 조회 화면은 월간 달력과 카테고리별만 남긴다 (주간·일간 제외). 정산하기는 계산 기능(더하기, 빼기, 1/n)으로 바꾼다. 계산 기능에는 곱하기, 1/n 끝전 처리(10원·100원 단위 올림·버림), 계산식 메모 기록을 더한다 (할인율·환율 환산 제외). 간단한 통계는 카테고리별 화면에 합친다 (선택한 기간의 합계와 카테고리 비중). 정기지출·할부는 MVP에 포함한다 | 1    |
| 카테고리        | **고정 목록 10개 (결정됨):** 식비, 가전, 교통, 의료, 의류, 미용, 문화, 교육, 생활, 기타                                                                                                                                                                                                                                                                      | 1    |
| 화면 구조       | 화면과 내비게이션 구성, 상세·수정을 모달로 할지 페이지로 할지                                                                                                                                                                                                                                                                                                | 2    |
| 디자인          | 디자인 토큰, 폰트(CDN 또는 직접 호스팅), 다크 모드                                                                                                                                                                                                                                                                                                           | 2    |
| 인증            | 인증 제공자 (Firebase Auth, Auth.js, Supabase Auth 등), 소셜 로그인 종류, 세션 방식                                                                                                                                                                                                                                                                          | 3    |
| 데이터 저장소   | **Next.js 서버 + Prisma + 관리형 PostgreSQL(Neon) (결정됨).** 구버전 Firebase 프로젝트는 재사용하지 않고, 오프라인 기록 기능은 필요 없다                                                                                                                                                                                                                     | 3    |
| 데이터 모델     | 소유자 키(uid), 금액·날짜 타입, 카테고리 관리 방식(고정 Enum 또는 사용자 정의)                                                                                                                                                                                                                                                                               | 3    |
| 데이터 조회     | 서버 기준 기간 조회와 집계, 캐싱 전략 (TanStack Query)                                                                                                                                                                                                                                                                                                       | 3    |

| 데이터 이전     | **옮긴다 (결정됨).** 새 계정을 만든 뒤 본인 데이터를 그대로 옮긴다. 방법은 3단계에서 정한다                                                                                                                                                                                                                                                                  | 3    |
