# 개발 준비

5단계(기능 단위 개발)에 들어가기 전에 갖출 도구·기반 코드·규약을 정한 문서다. **정본**이다. 5단계 기능 순서는 `2026-11-02-02-implementation-plan.md`.

- 입력: 데이터 아키텍처(`docs/03-data/2026-11-02-01-data-architecture.md`), 디자인 토큰(`docs/02-screens/2026-11-02-02-design-tokens.md`), 화면 명세·와이어프레임(`docs/02-screens/`)
- 진행 상태는 7장 체크리스트로 관리한다

## 1. 결정 요약

| #   | 항목           | 결정                                                                                                                                         |
| --- | -------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| P1  | git hook       | lefthook                                                                                                                                     |
| P2  | DB 통합 테스트 | 로컬 Docker Postgres. CI는 GitHub Actions Postgres 서비스. E2E도 같은 방식                                                                   |

### 2-2. 포맷·린트·타입

- **Prettier 3**: `prettier-plugin-tailwindcss`(설치돼 있음)로 클래스 순서를 정리한다. `.prettierignore`에 `docs/**/*.html`, `docs/reference/`, `public/`, `pnpm-lock.yaml`, `src/generated/`.
- **ESLint 10**: flat config로 `eslint-config-next`의 `core-web-vitals`·`typescript`를 쓰고, `eslint-config-prettier`로 포맷 규칙 충돌을 끈다. `eslint-plugin-check-file`로 파일 이름 규칙(4장)을, `eslint-plugin-simple-import-sort`로 import 순서(4장)를 검사한다.
- **TypeScript**: strict는 이미 켜져 있다. `noUncheckedIndexedAccess`를 추가한다.

### 2-3. 테스트

| 층       | 도구                                   | 대상                                                                                                                 | 위치                         |
| -------- | -------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| 단위     | Vitest 5                               | 반복 기록 규칙(생성·수정·삭제·연장), 날짜·말일 맞추기, 검증 스키마, 금액 축약, 계산기, 제목 추천 거르기(앞부분·초성) | 대상 파일 옆 `*.test.ts`     |
| 컴포넌트 | Vitest + Testing Library (jsdom)       | 공통 컴포넌트 상태(CG), 폼 검증 표시                                                                                 | `*.test.tsx`                 |
| DB 통합  | Vitest `db` 프로젝트 + Docker Postgres | API 핸들러·쿼리·트랜잭션 (범위 수정·연장·탈퇴·소유권 404)                                                            | `src/server/**/*.db.test.ts` |
| E2E      | Playwright 1                           | 핵심 흐름: 로그인 → 등록 → 달력 반영, 반복 범위 수정, 탈퇴                                                           | `e2e/`                       |

- 반복 규칙 단위 테스트는 3단계 견본(`docs/03-data/2026-11-02-02-recurring-scenarios.html`)의 경우를 하나씩 옮긴다. 견본의 시뮬레이터와 실제 코드가 같은 결과를 내야 한다.
- DB 통합 테스트는 실행할 때마다 로컬 `mdiary_test`의 스키마를 비우고 마이그레이션을 다시 적용한다 (`vitest.db-setup.ts`). 로컬 테스트 DB가 아니면 지우지 않는다.
- 테스트 로그인(P3): `E2E_TEST_LOGIN=1`이고 운영이 아닐 때만 Better Auth 플러그인으로 `POST /api/auth/test-login`을 연다. 그 밖에는 플러그인을 붙이지 않아 경로가 없다. E2E는 `e2e/helpers.ts`의 `loginAsTestUser`로 쓴다.
- E2E는 로컬 `mdiary_e2e`를 쓴다. 시작할 때마다 비우고 마이그레이션을 다시 적용한 뒤 테스트 사용자를 만든다 (`e2e/global-setup.ts`). DB가 없으면 만든다.

### 2-6. CI (GitHub Actions)

`.github/workflows/ci.yml`

- 트리거: `renewal-main` 푸시, PR, 수동 실행(`workflow_dispatch`). 같은 브랜치의 이전 실행은 취소한다
- `check` job: pnpm install → `lint` → `format:check` → `typecheck` → `test` → `test:db`(Postgres 서비스) → `build` → `check:wireframes` → `check:tokens`
- `e2e` job: PR과 수동 실행에서만 (P6). Postgres 서비스 + Chromium. 실패하면 `test-results/`를 artifact로 올린다
- 비밀값이 필요한 단계는 두지 않는다. 환경 변수는 워크플로의 가짜 값으로 `src/env.ts` 검증을 통과시킨다

### 3-2. 환경 변수

`src/env.ts`에서 zod로 검증한다. 빠지면 서버가 뜨지 않는다. 이름은 데이터 아키텍처 2장 (`DATABASE_URL`, `DIRECT_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `CRON_SECRET`) + 테스트용 `E2E_TEST_LOGIN`. `.env.example`에 이름만 적어 커밋한다.

### 3-3. DB

- Prisma 7 + `@prisma/adapter-pg`. 앱은 Neon(`DATABASE_URL`), 테스트는 Docker Postgres에 같은 방식으로 붙는다.
- Prisma CLI가 붙는 DB는 `DB_TARGET`으로 고른다 (`prisma/db-url.ts`, 주소는 `prisma/dbUrlConstants.ts`): 없으면 Neon development(`DIRECT_URL`), `local`이면 Docker `mdiary_dev`, `test`면 Docker `mdiary_test`, `e2e`면 Docker `mdiary_e2e`.
- 마이그레이션은 로컬에서 만들고(`pnpm db:migrate`), Neon development에는 `pnpm db:deploy`로 적용한다.
- 첫 마이그레이션: 데이터 아키텍처 7장 스키마 + CHECK 제약 SQL.
- `docker-compose.yml`: Postgres 18 하나에 `mdiary_dev`(마이그레이션 작성)·`mdiary_test`(DB 테스트)·`mdiary_e2e`(E2E). 테스트 DB는 `prisma/reset-local-db.ts`로 비운다. Neon과 같은 메이저 버전을 쓴다.
- seed: SC-03① 10월 달력 기준으로 개발 데이터를 넣는다 (10월 42건 1,234,500원, 8월 812,000원, 넷플릭스·월세 정기 계속, 아이패드 할부). 주인은 테스트 사용자 `test@mdiary.local`(P3와 같은 사용자).

### 3-4. 인증

- Better Auth + Prisma 어댑터 + Google 제공자. 테이블은 Better Auth CLI가 만드는 정의를 스키마에 붙인다.
- 설정은 `src/server/auth.ts`, 경로는 `src/app/api/auth/[...all]/route.ts`, 클라이언트는 `src/lib/authClient.ts`.
- 세션: 30일, 쓰는 동안 하루에 한 번 연장한다 (데이터 아키텍처 4-5).
- `src/proxy.ts`(Next 16의 middleware): 세션 쿠키가 없으면 `/login?next=…`로 보낸다 (화면 명세 RT). 로그인한 채로 `/login`에 오면 `next`로 보낸다. `next`는 같은 사이트 경로만 받는다 (`src/shared/nextPath.ts`). 쿠키만 보므로 세션이 유효한지는 서버에서 `getSessionUser()`로 다시 확인한다.
- API는 세션이 없으면 `unauthorized()`로 401 `{ code: "UNAUTHORIZED" }` (`src/server/session.ts`).

### 3-5. 디자인 토큰·글꼴·아이콘

- 토큰 문서의 색(라이트·다크), 글자 크기(짝수), 간격, 모서리(6·8·14·20·full), 그림자를 `src/app/globals.css`의 Tailwind 4 `@theme` 변수로 옮긴다. 다크는 `data-theme`와 시스템 설정 둘 다 따른다 (SC-10 화면 모드).
- 화면 모드는 쿠키 `theme`(`system`·`light`·`dark`)에 둔다. 루트 레이아웃이 읽어 `html`의 `data-theme`를 그리므로 첫 화면부터 깜빡이지 않는다. `system`이거나 값이 잘못됐으면 `data-theme`를 두지 않는다 (`src/shared/themeConstants.ts`, `src/shared/theme.ts`).
- 글꼴: Noto Sans KR·Rubik은 `next/font/google`, Tenada는 `next/font/local` (P5).
- 아이콘: `src/assets/*.svg`를 svgr로 불러온다. 모두 `currentColor`라 글자색을 따른다.
- 토큰 점검: 토큰 문서와 `@theme` 값을 비교하는 `scripts/check-tokens.py`를 만들고, lefthook pre-commit과 CI에 연결한다.

## 4. 코드 규약

- 파일 이름 (`src`, ESLint `check-file`로 검사): 컴포넌트(`.tsx`)는 PascalCase(`GoogleSignInButton.tsx`), 그 밖의 `.ts`는 camelCase(`nextPath.ts`, `testLogin.ts`). Next가 정한 이름(`page.tsx`, `route.ts` 등)은 그대로. `src` 밖의 도구·설정 파일(`prisma/db-url.ts`, `e2e/auth.spec.ts` 등)은 해당 도구 관례를 따른다.
- 상수와 함수는 파일을 나눈다. 내보내는 상수(와 그 값에서 나온 타입)는 `{이름}Constants.ts`에 두고(`themeConstants.ts`, `sessionConstants.ts`), 그 상수를 쓰는 함수는 다른 파일에 둔다(`theme.ts`). `src` 밖에도 같은 규칙을 쓴다(`prisma/dbUrlConstants.ts`). 여러 화면·모듈이 두루 쓰는 상수는 `src/shared/sharedConstants.ts`에 둔다 (예: 화면 제목 `PAGE_TITLES`). 파일 안에서만 쓰는 값은 그 파일에 둔다.
- import 순서 (ESLint `simple-import-sort`, `pnpm lint --fix`로 정렬): 외부 패키지 → `@/` 경로(`@/assets/*`는 그 묶음의 맨 뒤) → 상대 경로 → 스타일 같은 부수 효과 import. 묶음 사이는 한 줄 띄운다.
- 함수는 화살표 함수로 선언한다 (`const fn = () => {}`). `function` 선언은 불가피한 경우만 쓴다. 컴포넌트도 화살표 함수로 만들고 파일 아래에서 `export default`로 내보낸다. ESLint(`func-style`, `prefer-arrow-callback`, `react/function-component-definition`)로 검사한다.
- 날짜는 `YYYY-MM-DD` 문자열로 다룬다. JS `Date`로 바꾸는 곳은 `src/lib/date`의 함수뿐 (데이터 아키텍처 3-1).
- DB 접근은 `src/server`에서만. Route Handler는 검증 → 세션 → 서비스 호출 → 응답만 한다.
- 검증 스키마는 `src/shared`에 두고 서버·클라이언트가 같이 쓴다.
- 화면 문구는 합니다체 초안. 사용자가 검토한다.
- 커밋은 사용자 요청 시에만, 한국어 메시지, AI 작성자 표시 없음 (CLAUDE.md).
